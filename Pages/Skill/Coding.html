CODE QUALITY

CODING

約 18 万行のエンジンを読みやすく保つために、規約を文書化し、依存を図と数字で確かめながら直しました。

01

OVERVIEW

概要

動いたら終わりにせず、VECTOR REIGN のエンジンを読みやすく直しやすい状態に保つために行った取り組みです。規約、依存図、監査の記録を残しながら進めました。

02

ARCHITECTURE

設計

  • 層の分離 : Core、Engine、Application、Editor に分け、下の層から上の層を参照しません。
  • 窓口を介する : エンジンからは、エディターを IDevTool としてだけ見ます。
  • 持ち主の木 : 多くのマネージャーを持ち主の unique_ptr にしました。必要なものは引数のコンテキストで配ります。
  • PCH の分割 : 層ごとにプリコンパイル済みヘッダーを分けました。

03

IMPLEMENTATION

実装

規約を決めて文書化する

命名、所有、依存、コメント、ECS、レンダーグラフなどの決まりを、約 890 行の文書にまとめました。

項目決まりねらい
命名引数 a_、ローカル _、メンバ m_、static s_変数の種類を、名前から読めるようにする
略語定着した略語だけを許可リストにする_texMgr のような独自の省略をなくす
Enumenum class のみ。型名は E から始める書き方をそろえ、Enum だと名前から分かるようにする
Namespaceディレクトリと対応させるコードの置き場所を名前から分かるようにする
所有権unique_ptr が基本。shared_ptr は理由があるときだけ誰が持ち主かをコードから読めるようにする
依存Editor → App → Engine → Core の一方向。逆向きは禁止層をまたぐ変更の影響を限定する

依存を見える形にしてから直す

  • クラスの依存図を Excalidraw 形式で自動生成し、層の逆流、循環、どこからでも書ける状態の3つを直す対象にしました。
  • 1フェーズ1テーマで進め、フェーズの終わりに起動、シーン読み込み、ゲームモードの往復、エディター操作を確認しました。
  • 呼び出し回数をコマンドで数え、各フェーズの前後で記録しました。
  • ログの呼び出しのように、ロジックが動かず効果の大きいものから手を付けました。

残すものは理由を説明できるようにする

  • シングルトンをゼロにすることは目的にせず、残す判断の基準を先に決めました。
  • MainEngine : アプリの入口なので残しました。
  • ResourceManager : ResourceRef<T> が値としてアセットに埋まり、引数で渡せないので、入口として残しました。
  • 残す予定だった D3D12Wrapper は、Device を引数で渡してみると持ち主に入れる方が素直だと分かり、やめました。

規約への適合を監査する

  • 機械的に判定できる項目はスクリプトで全数を出し、誤検出を目で除きました。設計に関わる項目はコードを読んで判断しました。
  • 修正の前後に同じ計測を当てて、件数の変化を記録しました。
  • 監査と機械的な修正には Claude Code も使いました。構造を変える修正は、内容を確認して判断しています。

以前の作品の反省を生かす

以前の作品の改善点VECTOR REIGN での対応
機能とアプリケーションを分けるCore、Engine、Application、Editor の4層に分離
オブジェクトが増えるたびにクラスが増えるECS とプレハブで、コンポーネントの組み合わせとして作る
命名規則の統一規約に定め、違反を数えて修正
クラスの機能分割ができていない武器の手、肩、発射方式、反動などをコンポーネントに分割
